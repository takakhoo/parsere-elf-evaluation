\section{Implementation}\label{sec:implementation}

\toolname is implemented as a single Python module of around 850 lines, with five external dependencies (\texttt{networkx}, \texttt{pydot}, \texttt{pyelftools}, \texttt{tqdm}, \texttt{cxxfilt}) and a parallel work pool that scales to all available cores.
Running \toolname requires Python 3.13 and a \QEMU user-mode build for the target architecture.
The analyst supplies the target binary, a grammar template for the input format, and optionally a path to \texttt{addr2line} for source-line attribution during manual evaluation.

\subsection{Corpus Generation}\label{sec:impl:corpus}

Grammar templates are written as nested data structures.
Each template node carries a production name and a set of alternatives.
At leaves, alternatives are concrete byte sequences.
At internal nodes, alternatives are ordered tuples of child templates.
\toolname recursively enumerates every combination through Cartesian product, producing a set of concrete parse trees that serialize to byte strings.

\textbf{Branching factor sets corpus size.}
The JSON template yields 27 instantiations (729 pairwise comparisons), the URI template yields 1{,}458 instantiations (over two million pairwise comparisons), and the ELF template yields 20 instantiations (380 pairwise comparisons).
The text-format templates are larger because the underlying grammars have more independently varying productions.
Each input remains small (under one kilobyte for the text formats, exactly 1{,}048 bytes for ELF), which keeps trace collection practical even when the input count grows.

\textbf{Adding a new format.}
A new format requires two pieces: a template definition and a harness binary that exercises the parser library under test.
The template plugs into the existing format dispatch.
The harness compiles into the Docker image alongside the existing harnesses.
No changes to the core pipeline are needed.

\subsection{Tracing with QEMU}\label{sec:impl:qemu}

Each input is fed to the target via standard input.
\toolname invokes \QEMU with the basic-block logging flag enabled and a per-input output path, parses the resulting log with a regular expression that matches \QEMU's basic-block records, and constructs a basic-block object per record.
Only blocks within the target binary's executable segment are retained; blocks from the dynamic linker and the \QEMU runtime itself are discarded by checking each address against the target's PT\_LOAD program header.

Traces for inputs with non-zero exit status are excluded.
This ensures that the CFG is built from successful parses, where the parser exercises its full grammar-handling logic.

\textit{[BEN: the basic-block log format depends on the QEMU version. The current regex was written against QEMU 8.x as packaged on Debian bookworm. Worth pinning the version in the artifact description, or adding a fallback regex for older versions.]}

\subsection{Target Harnesses}\label{sec:impl:harness}

For each parser under test we compile a small C harness that links against the parser library, reads input from standard input, invokes the top-level parse function, and returns the result.
Harnesses are typically twenty to thirty lines.
The ELF harness is longer (around one hundred lines) because libelf exposes the parser as a family of small calls (one per program header, one per section header, one per symbol) rather than a single top-level entry point, and the harness must call all of them to exercise the full structure.

\textbf{Static linking is required.}
Dynamic linking caused the first URL evaluation to produce zero labels: the dynamic linker startup ran on every input, dominated every trace, and \toolname's uniqueness filter consequently wiped the entire graph as shared code.
Rebuilding curl from source with \texttt{--without-shared} produced a static archive that the harness could link against, which restored the trace differential signal.
Every harness in the current evaluation links statically (libelf via the \texttt{-static} GCC flag, json-c via its \texttt{.a} archive from a CMake build, curl via its source-built static archive).

\textbf{Compilation flags.}
All harnesses compile with \texttt{-O0 -fno-inline} so the compiler does not collapse distinct parser functions into shared inlined code, which would destroy the correspondence between grammar productions and basic-block ranges.
We also use \texttt{-no-pie} to keep addresses stable so that \texttt{addr2line} resolves cleanly against the binary on disk, and \texttt{-g} for debug symbols.

\subsection{Supported Formats}\label{sec:impl:formats}

The current implementation includes grammar templates for four formats:

\begin{itemize}
    \item \textbf{URI} (regular): scheme, authority (userinfo, host, port), path, query, fragment, per RFC~3986.
    \item \textbf{JSON} (context-free): objects, arrays, strings, numbers, booleans, null, per RFC~8259.
    \item \textbf{HPACK} (context-sensitive binary): indexed headers, literal headers with and without Huffman compression, per RFC~7541. \textit{[BEN: describe your template choices here when ready.]}
    \item \textbf{ELF} (offset-driven binary): one fixed ELF header, four program-header variants, five section variants. Each instantiation is a valid 1{,}048-byte ELF64 file constructed by a Python generator that keeps the inter-field offsets consistent across all twenty corpus members.
\end{itemize}

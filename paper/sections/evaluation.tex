\section{Evaluation}\label{sec:evaluation}

We evaluate \toolname on four input formats to assess both the generality of the technique and the accuracy of the labels it produces.
For each format, we run \toolname against one or more real-world parser implementations, then manually inspect every labeled basic block to determine whether the label is correct.

\subsection{Methodology}

For each format-parser pair, we:
\begin{enumerate}
    \item Compile a minimal harness linking against the parser library, inside a Docker container, with debug symbols enabled.
    \item Run \toolname with the corresponding grammar template under \QEMU user-mode emulation.
    \item Manually inspect the output: for every labeled edge and node, a human evaluator checks whether the source-code location (obtained via \texttt{addr2line}) implements the grammar production indicated by the label.
    \item Record true positives (correct labels), false positives (incorrect labels), and false negatives (unlabeled blocks that should have been labeled).
\end{enumerate}

This evaluation is labor intensive but avoids the pitfalls of automated evaluation.
A previous iteration of this work used a large language model for label verification and achieved roughly 50\% accuracy, which is insufficient for a credible evaluation.
All results reported here are from manual human inspection.

\subsection{URI Parsers}\label{sec:eval:url}

We evaluate on two URI parsers:
\begin{itemize}
    \item \textbf{Curl} (\texttt{curl\_url\_set}): the URL parser used by the Curl HTTP client, one of the most widely deployed URL parsers in existence.
    \item \textbf{Apache APR} (\texttt{apr\_uri\_parse}): the URI parser in the Apache Portable Runtime, used by the Apache HTTP Server.
\end{itemize}

The URI grammar template instantiates 1{,}458 distinct inputs varying across scheme, authority components (userinfo, host type, port), path segments, query, and fragment, which yields 2{,}125{,}764 pairwise comparisons.

On Curl's \texttt{curl\_url\_set}, \toolname produces a labeled CFG with 522 nodes and 558 edges, of which 211 basic blocks receive labels across 11 URI grammar productions.

\subsection{JSON Parsers}\label{sec:eval:json}

We evaluate on json-c, a widely used C library for JSON parsing (\texttt{json\_tokener\_parse}).

The JSON grammar template covers objects (with key-value pairs), arrays, strings, numbers (integer, floating-point, negative, scientific notation), booleans, null, nan, and inf.
It instantiates 27 distinct inputs and 729 pairwise comparisons.

\subsection{HPACK Decoder}\label{sec:eval:hpack}

HPACK~\cite{rfc7541} is the header compression format used in HTTP/2.
It encodes headers as variable-length integers and optionally Huffman-compressed strings, with a dynamic table for previously sent headers.
This format presents a stress test for \toolname: it is fully binary (no human-readable text), uses context-sensitive encoding (integer bit-widths depend on the header type), and involves compression (a fixed Huffman table defined in the specification).

\subsection{ELF Parser}\label{sec:eval:elf}

The Executable and Linkable Format (ELF) is the standard binary format on Linux and other Unix-like systems.
Unlike the sequential text formats above, ELF is offset driven: the ELF header contains pointers to program header and section header tables, which in turn point to string tables, symbol tables, and other sections.
We target libelf from elfutils, the reference library used by Ghidra, radare2, and most binary analysis toolchains.

The ELF grammar template has three children: a fixed ELF header (1~variant), program headers with 4~alternatives varying the second program header type (\texttt{PT\_NOTE}, \texttt{PT\_INTERP}, \texttt{PT\_DYNAMIC}, \texttt{PT\_NULL}), and section data with 5~alternatives that toggle the presence of symbol tables, string tables, and code sections.
This yields $1 \times 4 \times 5 = 20$ instantiations and 380 pairwise comparisons.
Each instantiation is a valid 1{,}048-byte ELF64 file with a fixed layout, generated by a script that constructs the headers, sections, and data in lockstep.

On libelf, \toolname produces a labeled CFG with 358 nodes and 354 edges.
Of these, 68 basic blocks receive the \texttt{section\_header} label.
The \texttt{program\_header} production receives zero labels despite having four template variants.
This reflects a fundamental property of binary format parsing: libelf reads all program header types through the same code path, because the type field is data stored in a struct rather than a dispatch key that selects between alternative parsing routines.
Section types do trigger different code paths: sections with symbol-table type cause the harness to iterate symbol entries, while null sections skip this work entirely.

The high ambiguity rate (202 blocks, 74.8\% of the labeled graph) reflects the structure of libelf.
Most of its code (memory allocation, data conversion, error checking) is shared across all section types.
The labeled blocks concentrate in libelf's section-data initialization routine and the harness's conditional symbol-table iteration loop.

This result reveals a meaningful contrast with text-format parsers.
Text formats like JSON and URIs require different parsing code for each production (string escaping has no overlap with numeric parsing), which yields many labeled productions.
Binary formats like ELF use uniform record readers for most structures, with variation appearing only in the consumer code that processes the parsed data conditionally.
\toolname captures this distinction without anyone having to tell it.

Manual inspection of all 68 labeled blocks yields 62 true positives (91.2\% accuracy) and 5 false positives.
The false positives are in an internal libelf header-validation routine that is called incidentally during section traversal.
These blocks process the ELF header rather than section headers, but are reached only through section-handling code paths.
No false negatives were identified: unlabeled blocks in the graph correspond to genuinely shared code (memory allocation, common initialization) or type-uniform readers.

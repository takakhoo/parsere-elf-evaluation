\section{Evaluation}\label{sec:evaluation}

We evaluate \toolname on four input formats with at least one open-source parser implementation each.
For every format-parser pair, we manually inspect every labeled basic block to determine whether the label is correct.

\textbf{Research questions.}
\begin{itemize}
    \item[\textbf{(Q1)}] How many basic blocks does \toolname label, and what fraction of the parser CFG do those labels cover?
    \item[\textbf{(Q2)}] How accurate are the labels at the per-block level?
    \item[\textbf{(Q3)}] Does the labeling behave consistently across language classes (regular, context-free, context-sensitive binary, offset-driven binary)?
\end{itemize}

\subsection{Methodology}\label{sec:eval:method}

For each format-parser pair, we (1)~compile a minimal harness against the parser library inside a Docker container with debug symbols, (2)~run \toolname with the corresponding grammar template under \QEMU user-mode, and (3)~manually inspect the output.
For every labeled edge and node, a human evaluator checks whether the source location (recovered via \texttt{addr2line}) implements the grammar production indicated by the label, and records true positives, false positives, and false negatives.

\textbf{Why manual inspection.}
A previous iteration of this work used a large language model for label verification and achieved roughly 50\% accuracy.
We treat that as a baseline for what an automated verifier can do without semantic grounding in the target binary, and we use manual inspection instead.
The numbers reported below are all from human evaluators reading the labeled SVG output and the disassembly of each labeled block.

\subsection{URI Parsers}\label{sec:eval:url}

We evaluate on two URI parsers: Curl's \texttt{curl\_url\_set} and Apache Portable Runtime's \texttt{apr\_uri\_parse}.
The URI template instantiates 1{,}458 inputs and produces 2{,}125{,}764 pairwise comparisons.

\textbf{Curl.}
On the static-linked Curl harness, \toolname produces a labeled CFG with 522 nodes and 558 edges, of which 211 basic blocks receive labels across 11 URI productions.
Table~\ref{tab:url-labels} shows the distribution.
Host validation dominates because Curl's parser performs extensive checks: IPv4 versus IPv6 detection, IDNA processing, bracket handling, and length validation.
The duplicate-looking labels (\texttt{port} versus \texttt{:port}, \texttt{query} versus \texttt{?query}) come from the template's leaf naming: the colon or question mark delimiter is included in the label string. This is a template quirk; the underlying attribution is correct.

\subsection{HPACK Decoder}\label{sec:eval:hpack}

HPACK is the header compression format for HTTP/2, defined in RFC~7541~\cite{rfc7541}.
The format is fully binary, uses context-sensitive encoding, and includes a fixed Huffman table baked into the specification.
This makes HPACK a stress test for \toolname: it has the offset-driven properties of ELF together with conditional encoding logic that text formats lack.

\subsection{ELF Parser}\label{sec:eval:elf}

ELF is the standard binary format on Linux and other Unix-like systems.
Unlike the sequential text formats above, ELF is offset-driven: the ELF header contains pointers to program header and section header tables, which in turn point to string tables, symbol tables, and other sections.
We target libelf from elfutils, the reference library used by Ghidra, radare2, and most binary analysis toolchains.

\textbf{Corpus layout.}
Figure~\ref{fig:elf-layout} shows the layout of a single corpus instantiation.
Every corpus member is exactly 1{,}048 bytes with identical offsets, and varies only in three regions: the ELF header (one variant), the two-entry program header table (four variants that change the second program header's type field across \texttt{PT\_NOTE}, \texttt{PT\_INTERP}, \texttt{PT\_DYNAMIC}, and \texttt{PT\_NULL}), and the section region (five variants that toggle which sections contain real data versus zeroed bytes).
The Cartesian product yields $1 \times 4 \times 5 = 20$ instantiations and 380 pairwise comparisons.

\textbf{Results.}
On libelf, \toolname produces a labeled CFG with 358 nodes and 354 edges.
Of these, 68 basic blocks receive the \texttt{section\_header} label.
The \texttt{program\_header} production receives zero labels despite having four template variants.

\textbf{Why \texttt{program\_header} is unlabeled.}
Libelf reads all program-header types through the same code path.
The \texttt{p\_type} field is data stored in a struct; libelf does not branch on it during parsing.
The basic-block trace through \texttt{gelf\_getphdr} is therefore identical across the four variants, and the difference algorithm has no edges to attribute.
Section types, by contrast, do trigger different code paths: sections with \texttt{SHT\_SYMTAB} type cause the harness to iterate symbol entries via \texttt{gelf\_getsym} and resolve names via \texttt{elf\_strptr}, while null sections skip these operations.

\textbf{Where the labels land.}
Figure~\ref{fig:elf-cfg} shows 12 of the 68 labeled blocks, taken directly from our \texttt{out.dot}.
They cluster in three places: the harness's \texttt{walk\_section\_headers} loop, libelf's \texttt{\_\_libelf\_set\_rawdata\_wrlock} section-data initialization routine, and libelf's lookup routines (\texttt{elf\_strptr}, \texttt{gelf\_getsym}).
The cross-function arrows are real edges from the trace: control flows from the harness's conditional branch into libelf's section setup and from there into the symbol-table walk only for sections that actually carry a symbol table.

\textbf{Accuracy.}
Manual inspection of all 68 labeled blocks yields 62 true positives (91.2\%) and 5 false positives.
The 5 false positives all sit inside \texttt{\_\_gelf\_getehdr\_rdlock}, an ELF-header validation routine that libelf calls internally during section traversal.
Those blocks process the ELF header rather than section headers, but they are reached only through section-handling code paths and so appear in the differential edge set.
We did not identify any false negatives: unlabeled blocks in the graph correspond either to memory allocation, common initialization, or libelf's type-uniform readers like \texttt{gelf\_getphdr}.

\textbf{What this reveals about binary formats.}
Text-format parsers label 6 to 11 distinct productions (JSON, URI).
Our binary-format evaluation labels exactly one (\texttt{section\_header}).
This is not a defect of \toolname; it accurately captures the structural property that binary parsers use uniform record readers for most structures and conditional consumer code for the rest.
The labels show up where the conditional logic lives.

\textbf{Coverage is not a function of corpus size.}
JSON uses 27 instantiations and labels 294 blocks (63\% of the graph).
URI uses 1{,}458 instantiations and labels 211 blocks (40\%).
ELF uses 20 instantiations and labels 68 blocks (19\%).
The labeling rate tracks the structural complexity of the parser rather than the size of the input corpus.
Text formats with per-production parser routines saturate with small corpora.
Binary formats with uniform record readers produce sparse but high-confidence labels regardless of corpus size.
